# AGENTS.md — ProMathStudio Autonomous Hourly Development Contract

This file is the durable operating instruction for the scheduled ProMathStudio developer. **Read it at the start of every run**, together with `docs/HOURLY_DEVELOPMENT_PLAN.md`, the [audited inventory](docs/FEATURE_INVENTORY_AND_MATLAB_GAP_ANALYSIS_2026-10-26.md), CI results, and the latest repository history. This file does not grant permissions or override security, CI, user controls or GitHub branch protection.

## Mission and cadence
- Develop ProMathStudio toward the 166-item gap inventory and improve the 95 partial features until verified at their **explicit mathematical scope**. Incorporate additional justified gaps into the plan without forgetting existing entries.
- Scheduled by ChatGPT Tasks **once each hour, indefinitely without a fixed end**. The task must remain enabled; only the user can choose to disable it. Individual executions may be interrupted by outages, task/service limits, permissions or safety requirements; resume at the next opportunity, **never bypass** those requirements. Do not claim work will continue when an execution is not actually scheduled.
- Each hour, select the highest-priority feasible small feature or correctness fix; implement source, tests, documentation and changelog, and **attempt** safe verified promotion/deployment. Report exactly what was committed/tested/merged/live, not imagined success.
- Do useful dev-branch work if CI or promotion is pending. A pending release is *not* a reason to stop coding. Work in compatible small increments and keep them tested.
- Maintain the **next five concrete upcoming features** in `docs/HOURLY_DEVELOPMENT_PLAN.md` on **every run**, with status, dependencies and acceptance tests.

## Repository and branch policy
- Canonical repository: `saeedsai/ProMathStudio`. Desired long-lived refs: **exactly `dev` and `main`**. `dev` is sole development branch; `main` contains only promoted and validated releases. No feature, fix, experiment, temporary or release branches. Do not force-push or rewrite published history.
- Before editing, inspect both heads and open PRs; if `dev` is absent, safely recreate it from `main`. If `main` advanced, reconcile it into `dev` without losing work. Resolve merge conflicts and rerun affected tests.
- Other branches inherited from older workflows are **cleanup candidates**, not authorized to discard unique commits. Delete them only if merged/contained in `main`, have no open PR, are unprotected, and write access permits it. Preserve unmerged contributions by integrating and testing them on `dev` first. Never delete `dev` or `main`.
- Preserve the runnable, self-contained `index.html`. Keep modular files in `src/` synchronized with inlined bundled code (see `scripts/build.py` and source-consistency tests). Do not upload vendored dependencies, generated caches, large datasets, or secrets.
- Repo cleanup: on each run inspect changed files and remove **tracked**, demonstrably obsolete build outputs, temporary/test fixtures and stale documents only after confirming nothing imports/references them. Update links/docs where needed. Do not erase unrelated historical data or contributor work.

## Mandatory loop on EVERY scheduled run
1. **Discover:** read this contract, latest inventory, short-term plan, test/CI status, current `dev`/`main` diffs, open PRs and outstanding blockers. Mark completed items using evidence; never infer feature completion from naming only.
2. **Choose:** select **one implementable bounded feature** (or highest-severity regression/security defect), state user-visible behavior and acceptance criteria, and confirm no existing duplicate implementation. Favor P0 foundational mathematical correctness.
3. **Implement on dev:** use smallest safe changes; retain current features, math domain assumptions, storage compatibility and offline functionality. Avoid arbitrary code execution from untrusted math; user Python only inside its explicit worker sandbox.
4. **Test every source commit:** add **at least one direct automated regression case** for new or changed behavior plus negative, boundary and integration cases when relevant. Run structural/unit suite, browser smoke and affected numerical, symbolic, graphs, spreadsheets, Python, navigation and project round-trip tests. Recheck previously fixed defects. Numerical tests need reference solutions, tolerances, residuals, domains, representative singularities and failure paths. Assert no console/runtime errors.
5. **Commit to dev:** small meaningful commits with test/doc updates; adjust affected docs and `CHANGELOG.md`. Do not mark acceptance complete when CDN, mobile, Word or network-dependent execution was mocked rather than actually verified.
6. **CI diagnose/recover:** check checks for the **exact dev head SHA**. Read failed job steps/logs; fix root cause on `dev`, add regression coverage and rerun. Never dismiss or bypass a failed check, reduce assertions merely to pass, turn off security checks, disable protections or force-merge. If permissions/CI outage blocks promotion, preserve a clean checkpoint and advance a separate compatible roadmap item on dev.
7. **CD/promote:** only when the exact candidate `dev` head has green full CI and relevant functionality is reasonably QA-verified, open/reuse **one PR from `dev` to `main`**, wait for PR required checks, inspect the diff, merge through authorized ordinary GitHub PR merge (no direct dev→main push, no force). Validate new `main` SHA, its quality workflow, GitHub Pages deploy/build status and, if tooling permits, live hosted critical paths. **GitHub Pages is configured to publish main**; existing optional `pages.yml` is manual. Do not call a release deployed until confirmed.
8. **Housekeeping:** keep `dev` up to date with merged `main`, remove only safely merged stray branches and verified temporary artifacts, ensure two-branch target persists, preserve README/AGENTS/docs links and project compatibility.
9. **Update living plan:** in every run update feature ledger (done/partial/blocked with commit/tests), append a concise execution log (date, exact SHAs, tests, blocker, deployment), and refresh the **NEXT FIVE** small implementable features in priority order. Unfinished feature remains in queue.
10. **Report:** state changed files, feature demo input, test status and links, dev/main SHAs, deployment evidence, blocked items and the next five. Never imply 166 items can be completed in a single run or that hourly tasks guarantee uninterrupted operation.

## CI/CD gates and failure handling
- `.github/workflows/quality.yml` runs on `dev` and `main` pushes, pull requests and manual dispatch. All relevant browser/structural tests must pass at the commit under consideration. New code adds a new test in `tests/`; workflow and Python test regression suites must not be silently skipped.
- An ordinary PR from `dev` to `main` is the promotion gate. Configure GitHub branch protection/rulesets to require checks, restrict direct `main` pushes and forbid force/deletion **when repository administration rights are available**; documents alone cannot enforce these settings. If protection cannot be configured, follow the manual no-direct-push rule and report the missing protection.
- Pages deployment occurs after merging main via its existing GitHub Pages publishing configuration. Check deployment run *and* published behavior; do not assume that passing CI equals live verification. Roll forward with a tested fix or restore by authorized non-force commit/PR; no force history rewrites.
- On blocked tool calls, rate limits, failed deploy, branch conflicts or infrastructure incident: record exact error and link, attempt authorized safe repairs, keep the scheduled task active, continue another useful incremental dev change. Revisit the issue next hour. Never circumvent OpenAI safety checks, credentials, approvals, GitHub protections or CI.
- Keep security/privacy intact: no unchecked Python from users in app main thread; avoid dynamic eval for math expressions; no secrets or personal data in logs. Dependency upgrades require lock/version review and regressions.

## Feature acceptance (Definition of Done)
A feature is **Done** only if: (a) clear UI/workflow exists, (b) mathematically valid for the published scope, (c) positive/negative/edge/reference tests are committed, (d) full required CI green for exact candidate, (e) documentation/feature inventory/changelog updated, (f) no existing features regress, and (g) merge and production Pages deployment were verified. Mark **Implemented on dev**, **In QA**, or **Released** distinctly; only the last is deployed. Features needing unavailable external hardware, proprietary toolboxes or services remain explicitly partial/blocked without fabricated completion.
